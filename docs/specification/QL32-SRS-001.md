# QL/32 — System Requirements & Architecture Specification

**Document ID:** QL32-SRS-001  
**Version:** 1.1
**Status:** Consolidated design baseline  
**Date:** 5 November 2026

## Vision

QL/32 is a compact, standalone BASIC computer combining an SMSQ/E-inspired
structured BASIC, Psion-inspired application interfaces, and native ESP32
services. It boots into an immediate programming environment and supports
graphics, storage, UI, networking, and hardware capabilities.

It shall not emulate Motorola 68000 hardware or execute QL ROMs, QDOS, or
SMSQ/E binaries.

## Architectural commitments

1. The BASIC grammar, compiler, VM, scheduler, and public APIs are portable.
2. Each interpreter runs in an independent session with owned resources.
3. Display, input, storage, audio, network, GPIO, and clock services are accessed only through platform-neutral interfaces.
4. The window manager and UI toolkit have no FabGL- or LVGL-specific public types; window canvases retain their contents independently and the compositor restores covered regions after overlapping windows move or close.
5. Firmware selects drivers through a board profile at build time.
6. Hardware-dependent APIs expose capabilities and fail gracefully when absent.

## CYD memory/concurrency characterization — closed 2026-11-08

The 2026-11-07 CYD tests establish a usable, profile-specific operating
envelope: two 320×240 4-bit canvases fit the 76,800-byte arena; a third is
rejected while general heap is still available. Ten animated 64×64 workers
ran near saturation; the next failed safely, with the supervisor responsive
and `SAVE` successful. Repeated cleanup showed no monotonic total-heap loss,
although free-block counts rose and ten-worker OOM passes sometimes left the
largest free block reduced after task reaping. The separate 25-run suite
returned to within 60 bytes of its total-free baseline after reboot; the
ten-worker saturation pass itself was not measured across reboot. A 320×240 eight-iteration render did
not finish within five minutes while array and channel workers were active, so
that combination is outside the interactive operating envelope. The
post-saturation allocation/fragmentation contribution is not isolated; report
the limitation without claiming a leak. Full checkpoints and caveats are in
[the CYD follow-up results](../test-results/CYD-open-points-2026-11-07.md) and
[platform status](QL32-PLAT-001.md). This closes characterization at the
measured operating-envelope level.

## Current open work, ordered by readiness

1. **Performance characterization:** Measure attractor frame time and actual
   ESP32 frequency for SINGLE/DOUBLE at 80/160/240 MHz. A benchmark variant is
   staged in `examples/attractor-benchmark.bas`. Tenstar YMODEM cancellation
   root cause was identified and fixed: the default USB CDC queue (256 bytes)
   was smaller than a 1,029-byte frame. A 2,048-byte queue passed an unpaced
   upload. The attractor benchmark has one 26.681-second sample at requested
   80 MHz/SINGLE; actual CPU frequency is not yet read back and three repeats
   are still needed. Separately, the bounded Mandelbrot workload had one
   33.929-second sample and later timeouts, so it has no reliable median.
2. **Board acceptance follow-up:** CYD rotations, graphics, task controls, FFS,
   dialogs and messages were retested. Tenstar display colors and rotations
   passed; Wi-Fi was skipped. Olimex and LILYGO physical acceptance checks were
   skipped by the user. See the dated board report for pass/not-run details.
3. **Olimex profile test:** Add a dedicated host test for its GPIO and FFS
   configuration; the Olimex target currently has no profile-specific CTest
   case. Previous physical checks remain documented, and latest follow-up was
   skipped by user choice.
4. **Other feature backlog:** Consider palette editing/cycling, BASIC
   `RND()`/`RND(value)`/`RND(low,high)` and `RANDOMIZE seed`,
   `DATA`/`READ`/`RESTORE` statements, an enhanced `DIR`
   listing with optional file sizes and `<subdir>` directory labels, string
   splitting/slicing, indirect calls, and network channels. BLE and new board
   families stay deferred until separately scoped.

   **System and capability introspection:** Consider BASIC functions such as
   `SYSINFO$`/`SYSINFO` with selectors in `ql32.inc` for the QL/32 product
   version, build identifier, platform family, and board/profile; and
   `CAPABILITY(query$)` for build/platform support such as SPI, I2C, or serial.
   CMake currently declares version `0.1.0`, but there is no BASIC-visible
   product/build identity API. The portable C++ `platform::Capabilities`
   descriptor already provides board profiles and service/input bitsets, but
   describes buses together rather than SPI and I2C separately, and is not
   exposed to the language. Define the authoritative product-version source,
   build-ID behavior when Git metadata is unavailable, host versus board naming,
   selector/query vocabulary, and whether a capability means compiled support,
   hardware presence, or current runtime availability. Keep the language API
   platform-neutral and return a stable false/unknown result for unrecognized
   queries.

   A candidate `SYSINFO$` selector set is `KSysVersion` (interpreter API
   version), `KSysBuild` (build identifier), `KSysPlatform` (stable build
   profile ID), `KSysDisplay`, `KSysInput`, `KSysStorage`, and `KSysFeatures`.
   Multi-value selectors may return comma-separated lowercase IDs; unavailable
   values may return an empty string. These values describe compiled profile
   capabilities, not live state such as mounted media or Wi-Fi association.
   Candidate platform IDs are:

   | `esp32-cyd-spiffs` | `ili9341-tft` | `usb-serial` | `spiffs` | `wifi` |
   | `esp32-lilygo-vga32` | `fabgl-vga` | `ps2` | `sd` | `wifi` |
   | `esp32-olimex-sbc-fabgl` | `fabgl-vga` | `ps2` | `spiffs,sd` | `wifi` |
   | `esp32-tenstar-s3` | `st7789-tft` | `usb-cdc` | `spiffs` | `psram,wifi` |

   Future S3 and P4 profiles remain provisional; expose only capabilities that
   are actually compiled and supported. Runtime measurements and states remain
   on existing APIs such as `FREE()`, `GWIDTH()`, and `NETSTAT$()`.

   **Shared display-buffer investigation:** An optional shared surface,
   controlled by a supervisor-only command and represented by QL/32 option
   flags, could reduce memory for tasks that intentionally draw into one
   display area. At 320x240 and 4 bits per pixel, each full-screen canvas uses
   38,400 bytes, before composed-frame or presenter storage. Before
   implementation, define which tasks may draw to the shared surface, how
   background drawing interacts with window visibility and overlap, and how
   switching modes treats existing retained canvases. Per-session retained
   canvases remain the default until those semantics are settled.

memory available on its platform. This is an expected per-session allocation
failure; it must not be converted into a fixed global task/window-count cap or
take down the scheduler.

## Resource allocation policy

Task and window creation are limited by actual platform allocation, not a
configured count or aggregate-canvas-byte ceiling. When an allocation fails,
the requesting task reports failure and releases its resources; unrelated
sessions and the supervisor remain usable. Constrained embedded profiles hold
an emergency heap reserve for error handling, task cancellation, and SAVE, and
temporarily release it only while those recovery operations run. Recovery
paths and periodic platform diagnostics must avoid allocations that can
terminate the system after an allocation failure.

The 2026-11-07 CYD test created ten live sin/cos workers beyond the former
four-window cap. The next worker failed without resetting the board; SAVE
succeeded under that pressure, and killing/reaping all workers returned the
supervisor to its prompt. The Olimex profile builds with this policy, but its
physical memory-boundary test remains open.

The CYD saturation follow-up found no monotonic free-heap decline across
repeated cleanup cycles. After a ten-worker OOM pass, `FREE(0)` and `FREE(1)`
could remain below the idle baseline and the largest block varied from 31.7 KiB
to 15.9 KiB between passes; reboot restored the idle baseline. This
post-saturation fragmentation/high-water effect is a documented limitation,
not an established leak. At the tested workload, two 320×240 4-bit canvases
(38,400 bytes each) fill the 76,800-byte arena; a third fails cleanly with
general heap still available. The eight-iteration full-screen Mandelbrot
fixture exceeded five minutes with array and channel workers active, so the
combination is outside the interactive performance envelope. See the
[CYD follow-up report](../test-results/CYD-open-points-2026-11-07.md).

## Acceptance principles

Linux is the first conformance host. Every supported platform shall pass the
shared interpreter, scheduler, UI, and filesystem conformance suite applicable
to its enabled capabilities.
