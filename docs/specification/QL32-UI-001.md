# QL/32 — User Interface Contract

**Document ID:** QL32-UI-001  
**Status:** M2–M4 portable services and Linux presenters implemented; async line presenter integrated in VGA32 and CYD firmware profiles; physical VGA32 presenter verification pending

The OPL model comes from [Programming Psion Computers](../reference/README.md).
QL/32 adopts declarative controls and menus, not OPL source compatibility.

QL/32 provides two portable UI levels:

1. Managed controls — `ALERT`, `CONFIRM`, and later declarative dialogs and menus (`DINIT`, `DEDIT`, `DINT`, `DCHECK`, `DIALOG`, `MINIT`, `MCARD`, `MENU`).
2. Drawing — later graphics windows and primitives such as `LINE`, `RECT`, `CIRCLE`, `TEXT`, `INK`, `PAPER`, and `CLS`.

### M3 graphics decisions

Each BASIC session receives one default graphics window, created lazily when
its drawing service is first used. M3 drawing coordinates are integer pixels
with `(0,0)` at the top-left of that window, following the Psion OPL graphics
model. Drawing outside the window is clipped. Ink and paper are palette
indices; the initial palette is the QL eight-color set in its standard order:
black, blue, red, magenta, green, cyan, yellow, and white. Palette editing and
cycling are deferred backlog features. The portable interface must own
per-session drawing state and must not expose platform graphics types.

This is a QL/32 design choice, not a SuperBASIC or OPL source-compatibility
claim. The QL/SMSQ/E normalized graphics coordinate model differs. `RECT` and
`TEXT` are also QL/32 command spellings; OPL uses its own `g*` graphics
keywords. QL/32 uses command syntax `INK index`, `PAPER index`,
`LINE x1,y1,x2,y2`, `RECT x,y,width,height`, `CIRCLE cx,cy,radius`,
`TEXT x,y,text$`, `ROTATE degrees`, and `CLS`. Rectangles and circles are outlines; text coordinates identify its
top-left; clear fills with the current paper color. The OPL manuals inform
window ownership and interaction design. The Linux debug adapter writes a
640x480 SVG snapshot per session when the interpreter closes; it preserves the
QL palette and clips drawings to the window. It is an export for host testing,
not an interactive window manager.

`ROTATE degrees` selects a supported display orientation. `GWIDTH()`,
`GHEIGHT()`, `GDEPTH()`, `GROTATION()`, and `GPALETTESIZE()` report current
window properties; `GPALETTE$(index)` returns an indexed color as `#RRGGBB`.
Rotation is currently implemented by the CYD TFT adapter. The portable
contract reports unsupported rotation on adapters that cannot rotate.

UI is keyboard-operable, session-owned, and automatically laid out. Dialog
edits are transactional: values update BASIC variables only after confirmation.
Modal UI blocks the owning session's interaction, not the entire system.

## Planned BASIC catalogue

| Milestone | Commands | Purpose |
| --- | --- | --- |
| M2 | `ALERT`, `CONFIRM` | Standard message and confirmation |
| M3 | `INK`, `PAPER`, `LINE`, `RECT`, `CIRCLE`, `TEXT`, `CLS`, `ROTATE`, `GWIDTH`, `GHEIGHT`, `GDEPTH`, `GROTATION`, `GPALETTESIZE`, `GPALETTE$` | Drawing and window properties through portable services; CYD rotation |
| M4 | `DINIT`, `DTEXT`, `DEDIT`, `DINT`, `DFLOAT`, `DCHOICE`, `DCHECK`, `DBUTTONS`, `DIALOG`, `DGET$`, `DGET` | Declarative dialogs and typed result access |
| M4 | `MINIT`, `MCARD`, `MENU` | Declarative menus with stable command IDs |
| M4+ | `MCASC`, `MPOPUP`, `DFILE` | Extended controls |

Standard controls shall have system-managed layout, focus, validation, and
keyboard navigation. Esc cancels without changing BASIC variables; confirmation
commits edited values. Menu shortcut keys are separate from command identity.
Each window, dialog, and menu belongs to a session and is released when that
session ends. A waiting UI request suspends only that session.

### M4 declarative UI service model

The portable service accepts dialog definitions as ordered fields (`Text`,
`Edit`, `Integer`, `Float`, `Choice`, `Check`) and menus as ordered items with
stable nonzero command IDs, labels, shortcuts, and enabled state. A dialog
submission returns typed field values together as one result; cancellation
returns no values, allowing the VM to preserve transactional edits. Menu
selection returns the stable command ID, independent of shortcut spelling or
item position. Definitions and results are session-owned and travel through the
same asynchronous request queue as M2 alerts and confirmations. The Linux
console presenter renders each field type and menu selection for manual host
testing. The ESP32 line presenter handles alerts, confirmations, typed dialog
fields, and menu selection without blocking the firmware loop; replies arrive
as input lines. It is integrated for serial input on CYD and serial/PS/2 input
on VGA32. Linux tests cover the presenter state machine and VM
suspension/resumption. This adapts the OPL interaction model without promising
OPL source compatibility.

### M4 BASIC builder calls

QL/32 uses numeric handles returned by builder functions. Handles and builder
definitions belong to the interpreter session and remain available across REPL
entries until the interpreter is reset or the session closes. Field and menu item positions are
one-based in BASIC; menu command IDs are explicit stable integers.

```basic
dialogHandle = DINIT(title$)
DTEXT dialogHandle, label$
DEDIT dialogHandle, label$, initial$
DINT dialogHandle, label$, initial, minimum, maximum
DFLOAT dialogHandle, label$, initial, minimum, maximum
DCHOICE dialogHandle, label$, initialChoice, "Red|Green|Blue"
DCHECK dialogHandle, label$, initialState
DBUTTONS dialogHandle, acceptLabel$, cancelLabel$
accepted = DIALOG(dialogHandle)
name$ = DGET$(dialogHandle, fieldNumber)
age = DGET(dialogHandle, fieldNumber)

menuHandle = MINIT(title$)
MCARD menuHandle, commandId, label$, shortcut$
commandId = MENU(menuHandle)
```

`DTEXT` adds a non-editable label and counts as a field position. `DINT` and
`DFLOAT` require inclusive minimum and maximum values. `DCHOICE` splits its
options at `|`; both its initial choice and `DGET` result are one-based.
`DCHECK` accepts numeric `0` or `1`. `DIALOG` suspends its calling session and
returns `1` after submission or `0` after cancellation. Submitted values become
available through `DGET$` for edit fields and `DGET` for numeric, choice, and
check fields. A cancelled dialog leaves the field values unchanged. Dialog
button labels default to `OK` and `Cancel` and can be replaced with `DBUTTONS`.
`MENU` likewise suspends and returns the selected command ID, or `0` if
cancelled. `MCARD` currently creates enabled items; dynamic enable/disable and
cascading menus remain deferred.

### M2 asynchronous request contract

The portable `ql32::ui::Service` begins alert and confirmation requests without
blocking the caller. Each request belongs to one session and receives a unique
request ID. A platform adapter dequeues it, presents the native UI, and resolves
it with acknowledgement, confirmation, or cancellation. Polling returns no
result while pending and consumes a completed result once. Canceling a request
or ending its session invalidates outstanding work. The host queue is
thread-safe; adapters remain responsible for dispatching on their UI thread.

These APIs are intended for registered native calls above the VM. The BASIC
calls are `ALERT title$, message$` as a command and
`CONFIRM(title$, message$)` as a function returning numeric `1` for confirmed
and `0` for cancelled. Alert acknowledgement or cancellation lets the program
continue. These are QL/32 managed UI calls, not SuperBASIC or OPL source
compatibility claims.

`Interpreter::executeResumable` returns `Suspended` when a request is pending;
the host dispatches the queued request and later calls `resume`. The VM retains
its instruction position, operand stack, call frames, loops, and arrays for
that session while suspended. A pending result does not block another
interpreter session. `execute` remains a convenience for programs that do not
suspend; if one of these calls suspends, it reports that the host must use the
resumable API. Clearing or destroying an interpreter cancels its outstanding
requests. The BASIC parser and VM remain independent of FabGL, LVGL, or display
size.
