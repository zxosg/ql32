# QL/32 — User Interface Contract

**Document ID:** QL32-UI-001  
**Status (2026-11-01):** M2–M4 portable services, Linux/CYD/VGA32 retained-canvas compositor adapters, and the cooperative scheduler are implemented. Both ESP32 event loops drive a persistent interactive supervisor with bounded instruction slices. Embedded commands include `SPAWN`, `TASKS`, `TASKCHANNELS`, `LOGON`, `LOGOFF`, and `CANCEL`; workers retain their interpreter and channels at a prompt after startup. CYD hardware checks confirmed compositor behavior, rotations, persistent REPL state, numbered-program `RUN`, UI suspension/resume, and the supervisor flow: workers were started and cancelled, restarted, attached one by one after reaching their prompts, resized, and detached. Premature `LOGON` attempts while workers were still running were rejected as expected; no allocation errors occurred with the memory fix. The serial monitor confirmed task prompts and command processing; visual confirmation of all three display columns and channel-list contents remains with the user. Direct 1-, 4-, and 8-bit canvas checks measured constant free heap in every rotation. VGA32 display and presenter checks remain pending, and the board is unavailable.

The OPL model comes from [Programming Psion Computers](../reference/README.md).
QL/32 adopts declarative controls and menus, not OPL source compatibility.

QL/32 provides two portable UI levels:

1. Managed controls — `ALERT`, `CONFIRM`, and later declarative dialogs and menus (`DINIT`, `DEDIT`, `DINT`, `DCHECK`, `DIALOG`, `MINIT`, `MCARD`, `MENU`).
2. Drawing — later graphics windows and primitives such as `LINE`, `RECT`, `CIRCLE`, `TEXT`, `INK`, `PAPER`, and `CLS`.

### M3 graphics decisions

Each BASIC session receives one default graphics window, created lazily when
its drawing service is first used. M3 drawing coordinates are integer pixels
with `(0,0)` at the top-left of that window, following the Psion OPL graphics
model. Drawing outside the window is clipped. Ink and paper are palette
indices; the initial palette is the QL eight-color set in its standard order:
black, blue, red, magenta, green, cyan, yellow, and white. Palette editing and
cycling are deferred backlog features. The portable interface must own
per-session drawing state and must not expose platform graphics types.

### M4 window manager and compositor

Each visible graphics window has a retained canvas owned independently of the
physical display. The window manager owns portable properties such as screen
position, viewport size, visibility, and stacking order. Moving, resizing,
raising, hiding, or tiling a window updates those properties and recomposes the
affected screen region from the retained canvases. Overlapping windows may
cover one another visually, but drawing into one window must not alter another
window's retained content; when the covering window moves or closes, the
previously covered content is drawn again. The portable manager now implements
window ownership, bounds, visibility, stacking order, clipping, tiling, and
per-window indexed canvases at 1, 4, or 8 bits per pixel. New windows default
to 4 bits per pixel; 1-bit and 8-bit storage are explicit options. Linux, CYD,
and FabGL BASIC graphics services now draw pixels, geometric primitives, and
5x7 ASCII text into these canvases, then present the composed frame. The BASIC
command `WINDOW x,y,width,height` moves and resizes the current session's
window; content coordinates remain local to that window. `CLOSEWINDOW` releases
the current session's canvas and recomposes the display; later drawing creates
a new default window. The Linux CLI writes the composed output as a PPM image.

The startup reserves `#0` for the bottom CON-like command/error console and
keyboard input, and `#1` for user/program text output and graphics. Additional
channel IDs and unused window backing are allocated on demand to limit memory
use. `PRINT` and graphics default to `#1`; `INPUT`, command entry, and
system/error messages use `#0`. I/O and graphics commands accept an explicit
`#channel`, including `PRINT #channel,...`, `LIST #channel`, and
`CIRCLE #channel,...`. `CHANNEL #channel` changes the logical default for
unqualified output. `CHANNEL #source TO #destination` directly rebinds the
source handle to the endpoint currently bound to the destination. The binding
is shared, session-local, applies to all operations, and can be reset to the
source's original endpoint with `CHANNEL #source TO #source`. Thus, with
default `#1`, rebinding `#1` to a serial endpoint sends unqualified and explicit
`#1` text there; graphics report an unsupported-endpoint error. Changing the
default to `#0` selects `#0` for unqualified output; explicit selectors use
their handle's active binding. The runtime stores a one-step binding from each
logical handle to the active endpoint handle; it does not retain route chains.
Binding snapshots the destination's current endpoint, shares that endpoint's
state, and is reset by binding a channel to itself. Reserved handles and
opened file, serial-output, and null-output handles are implemented; serial
and null input remain future work.
`GETCHANNEL(KChannelCount)` returns the open-channel count, including reserved
`#0` and `#1`;
`GETCHANNEL(KChannelHandle, position)` returns the handle at that zero-based
position in ascending-handle order; `GETCHANNEL(KChannelType, #handle)` returns
symbolic endpoint type. These functions cover reserved channels and opened
file, serial, and null endpoints. The selector and device-kind constants are
supplied by the repository's `ql32.inc`. `LIST #1` draws in the output window,
`LIST #file` writes to a file, and `LIST #null` is discarded. The graphics
adapters expose the session output window as `#1`; future network channels
remain backlog work. The CYD fixed bottom text overlay is still separate from
a managed `#0` console window. Reserved-channel lifecycle and explicit
capability metadata remain outside the opened-endpoint registry.

The window manager is separate from the BASIC scheduler. A supervisory process
may move windows or request a tiled layout while BASIC sessions continue to
run. These operations must not change a window's BASIC drawing coordinates or
block other sessions. The public manager, canvas, and compositor interfaces
remain platform-neutral; CYD and FabGL code only presents the composed pixels.
The CYD and VGA32 event loops advance their persistent interactive session
through `SessionScheduler` in 128-instruction slices. They continue servicing
serial/keyboard input and UI replies between slices. `RUN` preserves its
interpreter state across ticks; an incomplete or failed entry returns control
to the prompt without replacing the session. The embedded REPL can start worker
sessions from storage with `SPAWN "path.bas"`, inspect them with `TASKS` and
`TASKCHANNELS id`, attach with `LOGON id`, detach with `LOGOFF`, and cancel
workers with `CANCEL id`. Workers remain interactive after their startup
source completes. Each session owns its interpreter state and channel handles;
they share the board adapters and physical display, storage, and serial
console. Worker `#0` text uses the console stream and `#1` output uses its own
graphics window. Hardware acceptance of concurrent sessions remains open.
The Linux compositor and PPM presenter provide the reference presentation
path. Embedded adapters bound retained canvas memory for their display and
report resource exhaustion cleanly. BASIC commands for controlling other
sessions' windows and requesting tiled layouts remain unfinished.

The first implementation maps one primary graphics window to each BASIC
session. Resizing preserves the upper-left portion of canvas pixels that still
fits and fills newly exposed pixels with the window's paper color. Multiple
windows per session and decoration style remain open design details. Embedded
profiles must set an explicit canvas byte budget. Packed 1-, 4-, and 8-bit
pixels use 1/8, 1/2, and 1 byte per pixel; a 640x480 canvas uses 38,400,
153,600, or 307,200 bytes, respectively, plus allocator overhead. All three
display targets now use 4-bit default canvases through the window manager. The
first eight QL palette entries remain
the defined BASIC colors. Linux uses fixed additional entries for 4- and 8-bit
canvases; user-editable palette commands and cycling remain backlog.
At the CYD's 320x240 resolution, the default 4-bit canvas uses 38,400 bytes;
at VGA32's 320x200 resolution, one uses 32,000 bytes.
Canvas resizing reuses the existing storage when its capacity is sufficient;
orientation changes that preserve the pixel count can therefore reshape a
full-screen canvas without allocating a second canvas-sized buffer. The CYD
releases its cached composed frame before a resize that needs additional
storage. Its TFT frame presenter now accepts composed rows and streams them to
the display, avoiding a 76,800-byte full-screen indexed frame allocation while
several task windows are active. Other frame presenters retain the full-frame
path.

This is a QL/32 design choice, not a SuperBASIC or OPL source-compatibility
claim. The QL/SMSQ/E normalized graphics coordinate model differs. `RECT` and
`TEXT` are also QL/32 command spellings; OPL uses its own `g*` graphics
keywords. QL/32 uses command syntax `INK index`, `PAPER index`,
`LINE x1,y1,x2,y2`, `RECT x,y,width,height`, `CIRCLE cx,cy,radius`,
`TEXT x,y,text$`, `ROTATE degrees`, and `CLS`. Rectangles and circles are outlines; text coordinates identify its
top-left; clear fills with the current paper color. The OPL manuals inform
window ownership and interaction design. The Linux CLI uses a 640x480
windowed graphics service and writes the latest composed frame to
`ql32-screen.ppm`. The older `SvgGraphics` adapter remains available for
per-session SVG export and host tests.

`ROTATE degrees` selects a supported display orientation. `GWIDTH()`,
`GHEIGHT()`, `GORIGINX()`, `GORIGINY()`, `GDEPTH()`, `GROTATION()`, and
`GPALETTESIZE()` report current window properties. Origin functions return
absolute top-left screen pixels; drawing coordinates remain window-relative.
`GPALETTE$(index)` returns an indexed color as `#RRGGBB`.
Rotation is currently implemented by the CYD TFT adapter. The portable
contract reports unsupported rotation on adapters that cannot rotate.

UI is keyboard-operable, session-owned, and automatically laid out. Dialog
edits are transactional: values update BASIC variables only after confirmation.
Modal UI blocks the owning session's interaction, not the entire system.

## Planned BASIC catalogue

| Milestone | Commands | Purpose |
| --- | --- | --- |
| M2 | `ALERT`, `CONFIRM` | Standard message and confirmation |
| M3 | `INK`, `PAPER`, `LINE`, `RECT`, `CIRCLE`, `TEXT`, `CLS`, `ROTATE`, `WINDOW`, `GWIDTH`, `GHEIGHT`, `GORIGINX`, `GORIGINY`, `GDEPTH`, `GROTATION`, `GPALETTESIZE`, `GPALETTE$` | Drawing and window properties through portable services; CYD rotation |
| M4 | `DINIT`, `DTEXT`, `DEDIT`, `DINT`, `DFLOAT`, `DCHOICE`, `DCHECK`, `DBUTTONS`, `DIALOG`, `DGET$`, `DGET` | Declarative dialogs and typed result access |
| M4 | `MINIT`, `MCARD`, `MENU` | Declarative menus with stable command IDs |
| M4+ | `MCASC`, `MPOPUP`, `DFILE` | Extended controls |

Standard controls shall have system-managed layout, focus, validation, and
keyboard navigation. Esc cancels without changing BASIC variables; confirmation
commits edited values. Menu shortcut keys are separate from command identity.
Each window, dialog, and menu belongs to a session and is released when that
session ends. A waiting UI request suspends only that session.

### M4 declarative UI service model

The portable service accepts dialog definitions as ordered fields (`Text`,
`Edit`, `Integer`, `Float`, `Choice`, `Check`) and menus as ordered items with
stable nonzero command IDs, labels, shortcuts, and enabled state. A dialog
submission returns typed field values together as one result; cancellation
returns no values, allowing the VM to preserve transactional edits. Menu
selection returns the stable command ID, independent of shortcut spelling or
item position. Definitions and results are session-owned and travel through the
same asynchronous request queue as M2 alerts and confirmations. The Linux
console presenter renders each field type and menu selection for manual host
testing. The ESP32 line presenter handles alerts, confirmations, typed dialog
fields, and menu selection without blocking the firmware loop; replies arrive
as input lines. It is integrated for serial input on CYD and serial/PS/2 input
on VGA32. Linux tests cover the presenter state machine and VM
suspension/resumption. This adapts the OPL interaction model without promising
OPL source compatibility.

### M4 BASIC builder calls

QL/32 uses numeric handles returned by builder functions. Handles and builder
definitions belong to the interpreter session and remain available across REPL
entries until the interpreter is reset or the session closes. Field and menu item positions are
one-based in BASIC; menu command IDs are explicit stable integers.

```basic
dialogHandle = DINIT(title$)
DTEXT dialogHandle, label$
DEDIT dialogHandle, label$, initial$
DINT dialogHandle, label$, initial, minimum, maximum
DFLOAT dialogHandle, label$, initial, minimum, maximum
DCHOICE dialogHandle, label$, initialChoice, "Red|Green|Blue"
DCHECK dialogHandle, label$, initialState
DBUTTONS dialogHandle, acceptLabel$, cancelLabel$
accepted = DIALOG(dialogHandle)
name$ = DGET$(dialogHandle, fieldNumber)
age = DGET(dialogHandle, fieldNumber)

menuHandle = MINIT(title$)
MCARD menuHandle, commandId, label$, shortcut$
commandId = MENU(menuHandle)
```

`DTEXT` adds a non-editable label and counts as a field position. `DINT` and
`DFLOAT` require inclusive minimum and maximum values. `DCHOICE` splits its
options at `|`; both its initial choice and `DGET` result are one-based.
`DCHECK` accepts numeric `0` or `1`. `DIALOG` suspends its calling session and
returns `1` after submission or `0` after cancellation. Submitted values become
available through `DGET$` for edit fields and `DGET` for numeric, choice, and
check fields. A cancelled dialog leaves the field values unchanged. Dialog
button labels default to `OK` and `Cancel` and can be replaced with `DBUTTONS`.
`MENU` likewise suspends and returns the selected command ID, or `0` if
cancelled. `MCARD` currently creates enabled items; dynamic enable/disable and
cascading menus remain deferred.

### M2 asynchronous request contract

The portable `ql32::ui::Service` begins alert and confirmation requests without
blocking the caller. Each request belongs to one session and receives a unique
request ID. A platform adapter dequeues it, presents the native UI, and resolves
it with acknowledgement, confirmation, or cancellation. Polling returns no
result while pending and consumes a completed result once. Canceling a request
or ending its session invalidates outstanding work. The host queue is
thread-safe; adapters remain responsible for dispatching on their UI thread.

These APIs are intended for registered native calls above the VM. The BASIC
calls are `ALERT title$, message$` as a command and
`CONFIRM(title$, message$)` as a function returning numeric `1` for confirmed
and `0` for cancelled. Alert acknowledgement or cancellation lets the program
continue. These are QL/32 managed UI calls, not SuperBASIC or OPL source
compatibility claims.

`Interpreter::executeResumable` returns `Suspended` when a request is pending;
the host dispatches the queued request and later calls `resume`. The VM retains
its instruction position, operand stack, call frames, loops, and arrays for
that session while suspended. A pending result does not block another
interpreter session. `execute` remains a convenience for programs that do not
suspend; if one of these calls suspends, it reports that the host must use the
resumable API. Clearing or destroying an interpreter cancels its outstanding
requests. The BASIC parser and VM remain independent of FabGL, LVGL, or display
size.
